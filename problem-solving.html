Talk about a time you were blocked on a simple problem

The javascript kata problem I was stuck on for the longest was the deebee problem. The problem you are prompted with is you need to write code that removes all instances of the word buzz from the sentence "Help! buzz I'm buzz buzz surrounded buzz by buzz buzz bees!!". In a previous exercise a similar function had to be created to capitalise the first letter of every word in a sentence by splitting the string into separate words, mapping over the array of words and altering each of them before joining them back together, so I used that function as a starting point. It took me a while but I inevitably managed to get the function to work deleting the instances of buzz, using the filter method as suggested by the problem's premise question. The part of the challenge that I got stuck on was making the function work regardless of what capitalisation the buzzes used. I didn’t really grasp the differences between the map method used in the previous problem and the filter method used in this one. I was worried that if I used a method to make the incoming string lowercase the string that the function outputs would be altered. I spent quite a while trying things out based on this misunderstanding, vaguely trying to plainly write out what the best approach would be and where I might place functions to alter capitalization before deciding to take a break from writing code and just research how the filter function actually works. I quickly realised my mistakes and that I had been pulling on the wrong thread the entire time and was able to fix my code and correctly use the filter function. Unlike if I were using a map, entering the toLowerCase method within the filter method does not actually change the code, just what the filter is viewing and filtering out.

Discuss a time you elegantly solved a problem

A simple problem I had to solve during the javascript kata challenges was creating a javascript function that finds the average of an array of numbers. Because I am genuinely awful at maths, before even trying to solve the problem I had to search up and remind myself how to find the average of multiple numbers (dividing their total sum by the number of values in the list FYI). Then the problem became writing script that would enact that process. In problem solving during the kata challenges my general problem solving process has involved trying to write any code that I think could hypothetically work without any assistance and if it fails move on to pseudocoding and researching actual methods. I’m still trying to get a solid hold on a lot of the correct syntax and I’ve found quite a few times throughout the process that while my basic logic/instincts for what should be done is correct the way I write it out is causing me problems. The pseudocode/comment instructions I wrote for myself for the averaging function was this:

//for loop that goes through a given array (arr value)
// loop needs to count each number and create a total sum
// now we need to divide the total number by the number of values in the array (arr.length?) to get the average

The actual code I ended up writing looked something like this:

function average(arr) {
let totalSum = 0;
for (let i = 0; i < arr.length; i++) {
totalSum += arr[i];
}
return totalSum / arr.length;
}

I had to search up how to implement the += operator because the method I was using was not working in the way I intended but overall my final code functions fine. I’m sure there are ways it could be streamlined and at some point I would like to look into them.

Reflect on how confident you feel using each of these problem-solving techniques/processes:

Pseudocode

I feel mostly confident using pseudocode to clear up problems, I think it was something I was doing in my head a bit even before I typed it out into the document.

Trying something

I have been generally trying to start my approach to each problem by simply just trying things out as I think it is the most satisfying and reinforcing for my memory / knowledge of the code when I am successful in it.

Rubber Ducky method

I have been doing lots of my coding while my partner works in the same room and have resorted to explaining my problems out loud to her in place of a rubber duck.

Reading error messages

The error messages have been a helpful guide at points although for the first few problems I was struggling to read the UI within the terminal as I was not yet used to the format.

Console logging

I am confident using console logs, it is generally a useful tool, although not something I jump to immediately, I think because in the javascript kata I was using the test results and error messages for the same purpose I would be console logging things out.

Googling

Very useful, very confident in using, it is great to have full guides on any given topic or issue available nearly instantly.

Asking peers / coaches

I am confident in my ability to ask others, I have used the foundations help channel during foundations already. It is usually my last resort as answers from others often take time and I like to work on things in my own timeframe.

Improving your process with reflection

I do this regularly and I think it is generally just a part of my learning process that happens naturally.

Reflect on a time you were reluctant to ask for help

I was reluctant to ask for help during the second sprint, when I was having issues with my blog's responsiveness. I was reluctant to ask for help because I was having issues with it on the sunday of that week and I felt ashamed that I was still working late into the sprint. I also feel a degree of stubbornness about these things and I did inevitably fix my site in time for the hand in. My philosophy I have been sticking to since then has been to tackle as much of the sprints as early in the week as possible, so that when I run into problems there is plenty of time to reach out to facilitators and peers if needed.
